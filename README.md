# AWS Bedrock Multi-Agent Cloud Infrastructure System

A **supervisor + 7 specialist agent** architecture built on Amazon Bedrock.
All orchestration, dependency resolution, and inter-agent communication runs inside Bedrock — you only need to call the Super Agent.

---

## Architecture

```
User Request
     │
     ▼
┌─────────────────────────────────┐
│        Super Agent              │  ← Bedrock Supervisor
│  (CloudInfraSuperAgent)         │    Routes, sequences, synthesises
└──────┬──────┬──────┬──────┬─────┴──────┬──────┐
       │      │      │      │            │      │
       ▼      ▼      ▼      ▼            ▼      ▼
  ┌───────┐ ┌─────┐ ┌──────────────┐ ┌────────┐ ┌─────┐ ┌────────┐ ┌──────┐
  │  S3   │ │ IAM │ │Observability │ │Compute │ │ VPC │ │Database│ │FinOps│
  │ Agent │ │Agent│ │    Agent     │ │ Agent  │ │Agent│ │ Agent  │ │Agent │
  └───────┘ └─────┘ └──────────────┘ └────────┘ └─────┘ └────────┘ └──────┘
       │      │                            │        │         │        │
       ▼      ▼                            ▼        ▼         ▼        ▼
  Lambda  Lambda                       Lambda   Lambda    Lambda   Lambda
 (boto3)  (boto3)                     (boto3)  (boto3)   (boto3)  (boto3)
```

### Inter-Agent Dependency (example: VPC + IAM)

When the VPC Agent needs Flow Logs, it signals a dependency rather than failing:

```
1. User: "Create prod-vpc with flow logs"
2. Super Agent → VPC Agent
3. VPC Agent: { "requires_iam": true, "action": "create_vpc_flow_logs_role" }
4. Super Agent → IAM Agent: create_vpc_flow_logs_role
5. IAM Agent: { "status": "granted", "role_arn": "arn:aws:iam::..." }
6. Super Agent → VPC Agent (retry with role_arn)
7. VPC Agent: { "status": "created", "vpc_id": "vpc-...", "flow_logs": "enabled" }
8. Super Agent: consolidated summary to user
```

| File | Purpose |
|---|---|

## Prerequisites

### 1. AWS Account Setup

```bash
# Install dependencies
pip install boto3

# Configure credentials
aws configure
# or set environment variables:
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_REGION=us-east-1
```

### 2. Enable Bedrock Model Access

In the [AWS Console → Bedrock → Model access](https://console.aws.amazon.com/bedrock/home#/modelaccess):
- Enable: `Anthropic Claude 3.5 Sonnet v2`

### 3. Create the Bedrock Agent IAM Role

```json
// Trust policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "bedrock.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

Attach these managed policies to the role:
- `AmazonBedrockFullAccess`
- `AWSLambdaRole`

```bash
# Create role (replace with your AWS account ID)
aws iam create-role \
  --role-name BedrockAgentRole \
  --assume-role-policy-document file://trust-policy.json

aws iam attach-role-policy \
  --role-name BedrockAgentRole \
  --policy-arn arn:aws:iam::aws:policy/AmazonBedrockFullAccess
```

### 4. Deploy Lambda Functions

Create **7 Lambda functions** (Python 3.12 runtime):

| Function Name | AGENT_KEY env var |
|---|---|
| `bedrock-s3-agent` | `s3` |
| `bedrock-iam-agent` | `iam` |
| `bedrock-observability-agent` | `observability` |
| `bedrock-compute-agent` | `compute` |
| `bedrock-vpc-agent` | `vpc` |
| `bedrock-database-agent` | `database` |
| `bedrock-finops-agent` | `finops` |

Each function uses the corresponding `lambda_<agent>.py` code. Set the `AGENT_KEY` environment variable to route to the correct handler if using `lambda_handlers.py`.

Required Lambda execution role permissions (per function):

| Function | Required AWS permissions |
|---|---|
| S3 | `s3:*` |
| IAM | `iam:CreateRole`, `iam:AttachRolePolicy`, `iam:PutRolePolicy`, `iam:GetRole`, `iam:ListRoles` |
| Observability | `cloudwatch:*`, `logs:*`, `cloudtrail:*` |
| Compute | `ec2:RunInstances`, `ec2:Describe*`, `ec2:StopInstances`, `autoscaling:*` |
| VPC | `ec2:CreateVpc`, `ec2:CreateSubnet`, `ec2:CreateInternetGateway`, `ec2:CreateNatGateway`, `ec2:CreateSecurityGroup`, `ec2:CreateFlowLogs`, `ec2:Describe*`, `ec2:AllocateAddress` |
| Database | `rds:*`, `dynamodb:*` |
| FinOps | `ce:GetCostForecast`, `pricing:GetProducts` |

## Dependency Resolution Flow

The Super Agent automatically sequences dependent tasks. Here are the patterns it handles:

```
┌─────────────────────────────────────────────────────┐
│ Request: "Create VPC with Flow Logs"                │
├─────────────────────────────────────────────────────┤
│ Step 1: Super Agent → VPC Agent                     │
│         VPC Agent signals: { requires_iam: true }   │
│                                                     │
│ Step 2: Super Agent → IAM Agent                     │
│         IAM creates VPCFlowLogsDeliveryRole         │
│         Returns: { status: "granted",               │
│                    role_arn: "arn:aws:iam::..." }   │
│                                                     │
│ Step 3: Super Agent → VPC Agent (with role_arn)     │
│         VPC creates VPC + subnets + IGW + Flow Logs │
│         Returns: { status: "created", vpc_id: ... } │
│                                                     │
│ Step 4: Super Agent consolidates + reports to user  │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│ Request: "Launch EC2 in new environment"            │
├─────────────────────────────────────────────────────┤
│ Step 1: Super Agent → VPC Agent + IAM Agent         │
│         (parallel — independent tasks)              │
│                                                     │
│ Step 2: Super Agent → Compute Agent                 │
│         (uses subnet_id and instance_profile_arn    │
│          from steps 1)                              │
│                                                     │
│ Step 3: Super Agent → Observability Agent           │
│         Creates CPU/network alarms for new instance │
└─────────────────────────────────────────────────────┘
```

## MCP Server Integration

[Model Context Protocol (MCP)](https://modelcontextprotocol.io) extends agents with live data sources. While Bedrock doesn't natively support MCP clients, you can integrate MCP into each Lambda action group handler. Here's how:

### Option 1 — MCP in Lambda (recommended)

Each Lambda function can act as an MCP client, fetching context from an MCP server before executing AWS API calls.

```python
# Inside lambda_handlers.py
import httpx

MCP_SERVER_URL = os.environ.get("MCP_SERVER_URL", "http://mcp-server:8080")

def call_mcp_tool(tool_name: str, arguments: dict) -> dict:
    resp = httpx.post(
        f"{MCP_SERVER_URL}/tools/{tool_name}",
        json={"arguments": arguments},
        timeout=30,
    )
    return resp.json()

# Example: S3 handler enriched with MCP cost data
def handle_s3_create(params):
    # Fetch cost estimates from an MCP billing server
    cost_data = call_mcp_tool("get_s3_cost_estimate", {
        "region": params.get("region", "us-east-1"),
        "storage_class": "STANDARD",
    })
    # ... proceed with bucket creation
```

### Option 2 — MCP Servers to Add

| MCP Server | Provides | Which Agent Benefits |
|---|---|---|
| `@modelcontextprotocol/server-aws` | Live AWS resource inventory | All agents |
| `@cloudquery/mcp-server` | Cloud asset graph, compliance data | Observability, IAM |
| `@infracost/mcp-server` | Real-time cost estimates | Compute, S3, VPC |
| `@datadog/mcp-server` | Live metrics, incidents | Observability |
| `@hashicorp/terraform-mcp` | Terraform state context | All agents |
| Custom Git MCP | IaC configs, runbooks | Super Agent |

### Option 3 — MCP for Knowledge Context

Add a knowledge MCP server so agents can query runbooks, architecture diagrams, and compliance rules before making decisions:

```python
# In each Lambda handler
def get_runbook_context(operation: str) -> str:
    """Fetch relevant runbook from an MCP knowledge server."""
    resp = call_mcp_tool("search_runbooks", {"query": operation})
    return resp.get("content", "")

def handle_vpc(function_name, params):
    context = get_runbook_context(f"vpc {function_name}")
    # Agent now has runbook context before calling AWS APIs
    ...
```

### Deploying an MCP Server for Bedrock

```bash
# Run the AWS MCP server alongside your Lambda functions
docker run -p 8080:8080 \
  -e AWS_REGION=us-east-1 \
  mcp/aws-server:latest

# Set MCP_SERVER_URL in each Lambda environment variable
aws lambda update-function-configuration \
  --function-name bedrock-vpc-agent \
  --environment Variables={AGENT_KEY=vpc,MCP_SERVER_URL=http://mcp-server:8080}
```

## Troubleshooting

| Error | Cause | Fix |
|---|---|---|
| `ResourceNotFoundException` on invoke | Agent not prepared | Re-run `setup_agents.py` |
| `AccessDeniedException` in Lambda | Missing IAM permissions | Add permissions to Lambda execution role |
| `ThrottlingException` | Bedrock rate limit | Add retry with exponential backoff |
| VPC Flow Logs not enabled | IAM role not passed | Check Super Agent trace for IAM step |
| Lambda timeout | Slow AWS API call | Increase Lambda timeout to 60s |
| `ValidationException` in action group | Schema mismatch | Check function schema vs Lambda params |

## Comparison: Autonomous Agent vs Multi-Agent

| | Autonomous Agent | Multi-Agent (this project) |
|---|---|---|
| **Agents** | 1 | 1 super + 5 specialists |
| **Tools** | All tools on one agent | Scoped tools per domain |
| **Dependency handling** | Single agent reasons through it | Explicit inter-agent signalling |
| **Parallelism** | Sequential tool calls | Parallel collaborator invocations |
| **Best for** | Simple ops, scripting | Complex multi-domain provisioning |
| **Cost** | Lower (fewer API calls) | Higher (more agent turns) |
| **Auditability** | Single trace | Per-agent traces, easy to debug |
